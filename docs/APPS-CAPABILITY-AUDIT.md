The matrix below records the state **before the separate-app implementation began**. Its missing-capability statements are historical, not a description of the current source. At that audit point, no new routes, engine profiles, migrations, renders or tests had been added. This compares the 13 `panel-*` categories in the supplied `higgsfield-oss-ranked.html` with the implementation at that audit point. The HTML is research material, not instructions or proof of current live behavior; root's live interaction audit must settle the screen contracts. In particular, its Speak editor/script flow was explicitly inferred rather than directly observed.

## Existing backend boundaries

- `/api/assets` supports images and video streams, immutable IDs, content hashes, previews, frame extraction and downloads. Audio-only files are currently rejected. There is one source, one mask and one optional reference asset slot per render; references are model/task restricted.
- `/api/jobs` persists a single video render request, outputs, workflow, progress, cancellation, retry and favorites. One worker claims FIFO jobs serially. Restart recovery marks an interrupted render failed and never automatically resubmits a remote job. There are no parent runs, stages, dependency graphs, batch identities or app attribution.
- Current model/task catalog is LTX 2.3, LTX Fast 0.9.8 and Wan VACE: text-to-video, image-to-video, masked inpaint and restyle, subject to each profile. Ten effect entries are workflow/prompt presets, not ten separately trained capabilities. LTX profiles allow at most 241 frames, Wan 161, with model-specific frame/dimension alignment; do not advertise the HTML's long durations or 4K as current guarantees.
- `/api/presets` stores a named render recipe and deliberately clears all source/mask/reference IDs. It cannot serve as an app document, character library, moodboard, chat, shot list or canvas.
- Provider settings are shared and redacted. Provider checks distinguish installed/detected capabilities from actual execution. Hosted Cloud is native diffusion with explicit local processing; optional SAM2 needs the configured local runtime. No further Cloud renders are authorized for this task.
- Current frontend draft is one browser-local `openframe-draft`. The backend has no draft/document API. Reusing this one key for 13 screens would mix their inputs and lose independent app state.
- Asset deletion currently protects references from jobs only. New persisted documents must participate in reference protection before retaining asset IDs.

## Minimal additive persistence proposal — awaiting contract

1. Keep the existing render request, `/api/jobs`, engine graphs, stored execution provenance and worker semantics unchanged. Do not smuggle app settings through `RenderRequest`'s permissive extra fields: an accepted JSON field does not mean the model uses it.
2. Add one bounded **app document** table: `id`, `app_id`, `title`, `schema_version`, `revision`, `state_json`, `created_at`, `updated_at`. Support multiple saved documents per app, with validated per-app state schemas after live references are settled. Store immutable asset IDs, never file bytes, local paths or provider credentials. Debounce noncritical autosaves; use expected revision checks to prevent a stale browser tab from overwriting a newer document.
3. Add a small **job association** table: `job_id`, `app_id`, `document_id`, `document_revision`, optional `step_id` and `group_id`. These are provenance links to actual leaf render jobs, not a replacement job state machine. A scoped render submission must validate and create the existing job plus its association atomically. Existing unassigned jobs remain accessible; do not silently recategorize old work or rewrite old requests.
4. Minimal proposed endpoints are scoped document list/create/read/update/delete, app-scoped job listing, and a scoped wrapper for submitting a supported existing render. Exact paths and request schemas should be agreed with frontend after the reference audit. Extend asset-reference checks to saved documents. Document deletion should not delete its completed media or change existing job behavior.
5. Expose an explicit per-app operation/capability map backed by registered handlers. Separate “screen/draft available” from “operation configured” and “operation verified.” Missing image, speech, training or orchestration handlers must remain clearly unavailable; no fake results and no silent conversion to generic video generation.
6. Implement multi-stage orchestration only when its concrete app contract is approved. A Canvas dependency graph, training job or scripted narrator needs its own validated operation and durable stage semantics; it should not be forced into today's video `RenderRequest`. Independent UI screens do not themselves require separate databases, queues, duplicated media or duplicated settings.

Useful first separation: Cinema can expose supported single-shot video operations; Genjutsu can expose the existing masked-edit subset; selected mini-apps can expose the existing honest effect subset. The other categories need their own persisted forms/documents and additional real handlers before their Generate actions can meet the supplied product descriptions.
