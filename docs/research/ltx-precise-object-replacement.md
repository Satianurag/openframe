# LTX precise object replacement: released-workflow audit

Research date: 30 October 2026. This audit addresses the demonstrated toy-car → blue cuboid failure while the source moves from daylight into a tunnel. It is not a general model ranking. No weights were downloaded, no GPU inference was run, and author examples below are not our validation results.

## Recommendation

First reuse the **optional edited starting frame already present in the official LTX2.5 two-stage inpainting graph**. Our previous implementation retained masked-video conditioning but omitted this branch. It supplies actual cuboid appearance/geometry while retaining every masked source frame, unlike a text-only object instruction or a first-frame-only propagation model. It requires **zero additional model files**. Whether the cuboid remains rigid and follows the tunnel illumination is still an output question; the graph does not guarantee those properties.

The exact upstream source is [Lightricks' inpainting template, commit220e1d45aa0469f518e982102fca4dca92a61862](https://github.com/Lightricks/ComfyUI-LTXVideo/blob/220e1d45aa0469f518e982102fca4dca92a61862/example_workflows/2.5/LTX-2.5_ICLoRA_Inpaint_Two_Stage_Distilled.json). Preserve attribution to Lightricks. Its model stack is LTX2.5 distilled BF16, projected Gemma4, matching video/audio VAEs, and the explicitly compatible **LTX2.3 In/Outpainting0.9 IC-LoRA**. No invented2.5 adapter name or checkpoint-only substitution is involved. Code is Apache2; model files retain the LTX community terms and access requirements.

## Exact official branch and minimal integration

The pinned template exposes `start_image` and `use image input`; its preprocessing subgraphs make the mechanism explicit:

1. **Coarse:** `EmptyLTXVLatentVideo` → `LTXVImgToVideoInplace` (node3159, strength0.7), using `LTXVPreprocess` node5388 with compression18 → `LTXAddVideoICLoRAGuideAdvanced` node5114. That guide's image remains the masked original video, not a replacement still repeated through time.
2. **Refinement:** decoded/blended coarse result → Lanczos×2 → `VAEEncodeTiled` node5267 → `LTXVImgToVideoInplace` node5213 (strength1, original uncompressed edited image) → AV concatenation/refinement. The audio route remains separately selected.
3. Native `LTXVImgToVideoInplace` copies the encoded image into the first latent slot and sets its noise mask to `1-strength`; it is not merely a caption/reference hint. Native resizing center-crops if aspect ratios differ, so source and edited image must share the same fit/padding geometry.

Implementation in `engine/ltx25_workflows.py` therefore adds the branch only with explicit `inpaint_reference_mode='edited-first-frame'` plus one `reference_asset_id`. Native image dimensions must equal the source video's dimensions. The new input node fits once through the same FFmpeg scale/crop used for source frames, then the graph applies identical right/bottom refinement padding. It records the selected source trim, image SHA, fitted RGB SHA and actual stage sizes. Native coarse resizing then preserves the same padded aspect ratio. Existing final mask/plate compositing, source tracking, sampling schedules and the new audio/raw-output routes are unchanged. No-reference graphs must remain exactly equal.

The reference means **the edited full first frame at the selected trim**, not an isolated product photograph. Matching dimensions cannot prove semantic correspondence; the UI must show and the operator must review source/edited frame alignment. Later shape retention is not guaranteed. The first integration deliberately requires the published two-stage route rather than inventing a single-stage recipe.

## PaintAPlate: actual additional reusable implementation

Primary source: [AInVFX/ainvfx-paintaplate, commit31adafa85819b616c4f157dc88e6a96f5b9cfd9a](https://github.com/AInVFX/ainvfx-paintaplate/tree/31adafa85819b616c4f157dc88e6a96f5b9cfd9a), Apache2 code. Exact [workflow generator](https://github.com/AInVFX/ainvfx-paintaplate/blob/31adafa85819b616c4f157dc88e6a96f5b9cfd9a/tools/build_workflows.py) functions `clean`, `cleanup`, `shot`, `matte`, `comp`, `composite` and [mathops.py](https://github.com/AInVFX/ainvfx-paintaplate/blob/31adafa85819b616c4f157dc88e6a96f5b9cfd9a/mathops.py) are reusable code, not a paper-only proposal.

- `shot()` composes edited frame0 with the following source frames, native `LTXAddVideoICLoRAGuide`, Ripple strength1.35, eight Euler/simple steps, CFG1. For erase operations, the app passes the clean plate as that source.
- `matte()` tracks the generated object using `SAM3_VideoTrack`/`SAM3_TrackToMask`. `PaintAPlate_FollowMatte` also considers changed pixels near the painted seed, rejects distant components and holds a previous matte when tracking is missing. These fallbacks must remain visible diagnostics; a held matte is not a successful track.
- `PaintAPlate_FitToPlate` estimates bounded shifts outside the edit, applies a spatial log-color correction field, and smooths masks/shifts/color fields over neighboring frames. It can match a regenerated patch to a darkening plate. It cannot reconstruct a missing object or prove physically correct material response.
- The final `ImageCompositeMasked` restores the original plate outside the generated edit support. Their separate optional `RelightTransfer` changes the plate's lighting deliberately; it should not be silently enabled for a preserve-scene swap.

Our abbreviated Ripple path used the edited frame and native sampler but kept the **old source-object mask**, without this generated-object FollowMatte/FitToPlate pipeline or erase→insert staging. Therefore our failed tunnel result is not a complete validation of the entire author's app. Conversely, the author's examples do not establish that completing these stages will cure this specific failure. The README warns about foreground intersections, cast-shadow remnants and prompt-driven resurrection of erased objects. Its tested96GB GPU setup is not a promise for an ordinary lower-VRAM PC.

The actual Ripple adapter is [WepeNerd/LTX-Ripple@76abac5ede8a3415b9d1cd803843a38ecb351600](https://huggingface.co/WepeNerd/LTX-Ripple/tree/76abac5ede8a3415b9d1cd803843a38ecb351600), `LTX25_Ripple_v11.safetensors`,654,443,392 bytes, SHA256`bde543610144e5bba78782fb0ac18daa663fc087c2212244b8116deb1925ee2a`, LTX community terms.

The model card labels it Apache2; underlying LTX component terms still apply. The [author's release post](https://www.reddit.com/r/StableDiffusion/comments/1secygl/inpainting_with_reference_to_ltx23_mr2v/) explicitly says object-trained, experimental, and not trained for body/head/face replacement. ## Other primary workflows and delivery boundary

[Official2.5 Ingredients at the same pinned commit](https://github.com/Lightricks/ComfyUI-LTXVideo/blob/220e1d45aa0469f518e982102fca4dca92a61862/example_workflows/2.5/LTX-2.5_ICLoRA_Ingredients_Single_Stage_Distilled.json) holds a contact sheet on every guide frame using the2.3 Ingredients0.9 adapter. This is genuine persistent appearance conditioning, but the supplied graph does not simultaneously preserve a masked source video; combining adapters ourselves would be a new experiment.

[Official Layout-to-Render@bd765d5592f0ae78457162852a353b6a375cb00f](https://huggingface.co/Lightricks/LTX-2.5-22b-IC-LoRA-Layout-To-Render/tree/bd765d5592f0ae78457162852a353b6a375cb00f) supplies its own Comfy graph and expects a3D viewport/playblast carrying camera and object motion plus an art-direction first frame. Its claimed geometry alignment is relevant, but creating that missing3D driver is a different user workflow, not an existing drop-in for this plate.

Additional released Ripple graphs were located in [axiomgraph/ComfyUIWorkflow](https://github.com/axiomgraph/ComfyUIWorkflow/blob/e80123657a095b6866624c63161a2070962349c7/LTX%202_5%20Ripple_Flux_klein.json), EWOCvj2's first-frame-all-frames workflows and UoA-eResearch's native Ripple API wrapper. They do not establish a distinct solution to the observed failure and are not imported as redundant dependencies.

Normal PC delivery must include portable inputs, exact model/node manifests and attribution, with no evaluation compute node or credential requirement. The proposed sampling branch uses existing native nodes; our small file-validation/provenance helper ships in the existing local node pack. **Direct Comfy Cloud remains a separate availability question:** its fixed installed-node/model catalogue must contain the precise weights and nodes, or an explicitly documented local preparation/export route must replace helper nodes with native file inputs. Neither a isolated evaluation result nor our historical hybrid Cloud client proves that the complete standard graph runs wholly inside Comfy Cloud. No Cloud compatibility claim is made from this research.

## Explicit plate-fitting finish (30 October 2026)

The edited-start-frame LTX2.5 the reviewed job keeps the blue cuboid through the tunnel, but its original composite has a rounded brightness/color patch. Direct decoded RGB × recorded alpha + original plate reproduces that defect: the main cause is a generated/source lighting mismatch, not a new replacement object introduced by final compositing.

`custom_nodes/openframe/plate_fit.py` reuses the five Apache-2.0 PaintAPlate mathematical helpers (`shrink`, `_axis_taps`, `resize_to`, `push_pull`, `seam_field`) from the pinned source above, unchanged. A bounded two-pass wrapper estimates the log-RGB difference in an exterior ring, robustly clips samples, spreads the smooth field inward, bounds its ratio to exp(±0.4), and smooths it over five frames. Only generated RGB is corrected; the original floating alpha is composited once afterward. There is no mask expansion, grain addition, warp, object replacement, or multiplication of the original object into the edited interior. The full license accompanies the node pack.

The optional request `inpaint_composite_mode: "plate-fit"` is scoped to LTX2.5 Replace with original-background preservation. Missing/null remains `legacy`; the old API graph remains byte-structure identical. The new graph keeps sampling, conditioning and raw diagnostic unchanged, bypassing only the final Laplacian plate blend before this finishing node. Cloud retains its uncorrected native composite as a preview and applies the same explicitly identified CPU finishing on the host; it is not advertised as a hosted native node.

All97 existing decoded frames were processed without another model render. The production helper matches five reviewed full-frame PNGs exactly and preserves 52,888,023 alpha-zero pixel/frame positions exactly before video encoding. This removes the conspicuous rounded patch while retaining cuboid shape, fine texture and stable motion; warm tunnel tint is expected. A faint late sill mismatch remains. The released alignment step measured less than0.5px smoothed displacement and showed no material improvement, so alignment is omitted rather than adding unnecessary resampling. Existing outputs are preserved.  records this CPU-only comparison.
